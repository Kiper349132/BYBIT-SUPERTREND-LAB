BYBIT SUPERTREND LAB v0.7.1
=================================

ИСПРАВЛЕНИЕ v0.7.1 — ПАМЯТЬ И BROKENPROCESSPOOL
-------------------------------------------------
В v0.7.0 завершившиеся Future оставались в общем словаре до конца этапа.
Future продолжал держать свой полный пакет AutoResult в RAM даже после записи checkpoint.
На больших этапах память росла, после первого аварийного порога начинались частые flush,
а затем Windows могла завершить один worker и Python выдавал BrokenProcessPool.

v0.7.1:
- одновременно держит в работе не более ~2 задач на каждый worker;
- сразу удаляет завершившийся Future и его большой результат из памяти;
- после checkpoint реально освобождает пакет RAM;
- аварийная запись по RAM не срабатывает на каждом маленьком пакете;
- при BrokenProcessPool сначала принудительно сохраняет checkpoint и оставляет GUI живым;
- незавершённые блоки при следующем запуске пересчитываются, уже сохранённые пропускаются.

ВАЖНО ДЛЯ ПРОДОЛЖЕНИЯ С v0.7.0:
Если v0.7.0 успела сохранить checkpoint, скопируйте содержимое старой папки research\
в новую папку research\ v0.7.1. При тех же данных и настройках v0.7.1 распознает
незавершённое хранилище v0.7.0 и продолжит его. Папку data\ также можно скопировать.


ГЛАВНОЕ ИЗМЕНЕНИЕ v0.7.0
Программа больше не пытается держать миллионы полных результатов в оперативной памяти.

Полный поток исследования хранится на диске в папке:
    research\BTCUSDT_<идентификатор>\

Примерно каждые 1 000 000 полезных backtest-проверок программа:
1. записывает накопленные полные AutoResult в сжатый chunk_XXXXXX.jsonl.gz;
2. атомарно обновляет checkpoint.json;
3. очищает большой рабочий буфер из RAM;
4. оставляет в RAM только небольшой набор лучших/разнообразных кандидатов, необходимых для дальнейшего поиска.

Если этап заканчивается раньше миллиона проверок, он сохраняется сразу — ждать миллион бессмысленно, потому что завершённый этап должен быть восстановимым.
При высокой загрузке RAM (>86%) программа может сделать внеплановый ранний checkpoint для безопасности.
При критической загрузке RAM (~93%) программа делает безопасную остановку с checkpoint вместо попытки дойти до аварийного закрытия Windows.

CHECKPOINT / ПРОДОЛЖЕНИЕ ПОСЛЕ СБОЯ
- checkpoint.json хранит, какие части поиска уже полностью записаны.
- Для BASE единицей восстановления является один ATR-период внутри этапа.
- Для ADAPTIVE V2 режимы дробятся на небольшие независимые пакеты.
- При повторном запуске с теми же данными и настройками незавершённое исследование определяется автоматически.
- Программа пишет «НАЙДЕН CHECKPOINT» и продолжает сохранённый прогон.
- Максимальная потеря работы при жёстком аварийном завершении — текущий незаписанный пакет, обычно не более примерно 1 000 000 полезных проверок.

ЧТО ЛЕЖИТ В research\...
- chunks\chunk_*.jsonl.gz — полный сырой поток результатов исследования;
- stage_seeds\*.jsonl.gz — небольшие рабочие выборки для продолжения поиска;
- checkpoint.json — состояние незавершённого/завершённого прогона;
- research_index.json — итоговый компактный индекс завершённого исследования;
- README_RESEARCH.txt — пояснение структуры.

ВАЖНО: RETAINED_RESULTS_*.csv в папке results — НЕ полный набор миллионов стратегий. Это небольшая удобная выборка для интерфейса/отчёта. Полные результаты находятся в research\...\chunks.

ПОИСК
Поиск v0.6 сохранён и дополнен безопасным хранением:
- широкий базовый поиск LONG / SHORT / BOTH;
- отдельный поиск в ширину;
- fine-поиск вокруг лидеров SELECTION;
- cluster-wide;
- cluster-deep;
- ADAPTIVE V2: EMA + ADX + ATR separation + подтверждение + минимальное время удержания режима.

SELECTION / VALIDATION / DEVELOPMENT HOLDOUT
- SELECTION имеет право направлять дальнейший поиск.
- VALIDATION проверяет уже созданные варианты, но не выбирает новые области для углубления.
- DEVELOPMENT HOLDOUT исключён из research-score. Он уже анализировался в прошлых версиях и не считается новым неизвестным экзаменом.
- Настоящий fresh forward-test возможен только на новых свечах, появившихся после разработки текущей логики.

РЕЖИМЫ
- Стандартный — быстрый контрольный прогон.
- Глубокий — основной исследовательский режим.
- Максимальный — очень широкий и мелкий поиск; способен создавать десятки миллионов полезных проверок и требует заметного дискового пространства.

CPU И RAM
- BASE и ADAPTIVE V2 используют несколько процессов CPU.
- ADAPTIVE V2 разбит на небольшие задания, чтобы дочерний процесс не возвращал огромный список результатов одним куском.
- Статус показывает: этап, проверки, скорость, ETA, число процессов, сколько уже записано на диск, размер текущего буфера и процент занятой RAM.

РЕЗУЛЬТАТЫ
results\ содержит:
- RETAINED_RESULTS_*.csv — компактная рабочая/аналитическая выборка;
- TOP100_*.csv — итоговый TOP-100;
- RESEARCH_STORE_*.txt — путь к полному исследовательскому хранилищу и его объём.

reports\CHATGPT_REPORT_*.zip содержит:
- diagnostic_summary.json;
- research_storage_summary.json — сколько строк/проверок реально сохранено на диск;
- research_stage_counts.csv — точные durable-счётчики по этапам;
- checkpoint.json / research_index.json (не гигантские chunk-файлы);
- BASE vs ADAPTIVE V2;
- parameter coverage;
- кластеры и соседство параметров;
- overfit flags;
- development survivors;
- точный SELECTION/VALIDATION/HOLDOUT plan;
- Adaptive V2 regime diagnostics;
- сделки лидеров;
- исходные свечи и SHA-256;
- код программы и логи.

Гигантские research\chunks намеренно НЕ кладутся в CHATGPT_REPORT.zip — иначе отчёт мог бы весить гигабайты. Они остаются у пользователя и нужны для полного повторного анализа без пересчёта.

ЗАПУСК
1. Распаковать программу в отдельную папку.
2. При необходимости скопировать старые CSV истории в data\.
3. Запустить START.bat.
4. Выбрать режим.
5. Запустить исследование.
6. После завершения прислать reports\CHATGPT_REPORT_*.zip.

Если программа/Windows закроется во время исследования:
1. Не удалять research\.
2. Запустить ту же версию программы.
3. Оставить те же данные и настройки.
4. Нажать запуск исследования — программа должна найти checkpoint и продолжить.

ВАЖНЫЕ ОГРАНИЧЕНИЯ МОДЕЛИ
- Funding пока не учитывается.
- Просадка считается по закрытым сделкам, не по максимальной внутрисвечной плавающей просадке.
- Полная модель ликвидации и маржинальных уровней пока не реализована.
- Большое число тестов повышает риск случайных победителей; поэтому важны перенос SELECTION -> VALIDATION, устойчивость соседних параметров и fresh forward-test.
- Ни один исторический тест не гарантирует будущую прибыль.
